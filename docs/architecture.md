# ארכיטקטורה

## תמונה כללית

במרכז יושב **n8n**. אליו נכנסים אירועים, וממנו יוצאות פעולות לשירותים חיצוניים.

```
נכנס (טריגרים)              הליבה                יוצא (שירותים)
─────────────────         ──────────           ──────────────────
בוט טלגרם #1 (מנהל)   ┐                    ┌   Airtable (בסיס הנתונים)
בוט טלגרם #2 (לקוחות) │                    │   Gmail (מיילי מכירות)
Gmail (נכנס)          ├──►   n8n Cloud   ──┤   Google Drive (חשבוניות)
לוחות זמנים           │   סוכני AI          │
לוח בקרה / אפליקציה   ┘   מאגר וקטורי       └   OpenAI (מודלים)
```

## שכבת הנתונים — Airtable

ארבע טבלאות בשימוש, מתוך מודל רחב יותר: `Invoices`, `Leads`, `Products`,
`Tasks`. ראה [`../data/airtable-schema.md`](../data/airtable-schema.md).

הקשרים בין טבלאות הם **מפתחות זרים כטקסט** (למשל `CUST-0001`) ולא
קישורי Airtable — פשוט יותר, וקל יותר להצגה באפליקציה.

## שכבת הלוגיקה — n8n

### שלושת הסוכנים

**סוכן שירות לקוחות (WF5)** — מעוגן ב-RAG. מקבל שני כלי שליפה,
`policies` ו-`products`, ובוחר ביניהם לפי תיאור הכלי. ה-System Message
נגזר ממסמכי `07-agent-guardrails` ו-`08-customer-service-tone`.

**סוכן המנהל (WF9)** — בנוי הפוך. המספרים מחושבים **לפניו** בצמתי
Summarize ו-Aggregate, ולסוכן נשאר רק לנסח תשובה בעברית. כך אין לוגיקה
עסקית בתוך פרומפט, ואין סיכון שמודל שפה יטעה בחישוב. מוגן בשער זהות
לפי `chat.id` של הבעלים. לתשובה מצורף הקישור ללוח הבקרה.

**סוכן מכירות (WF4a / WF4b)** — מנסח מייל קר ומזהה תשובות. רץ ברקע
לפי לוח זמנים, בלי התערבות אנושית.

### RAG — איך זה עובד

1. **הכנה** — מסמכי המדיניות וקטלוג המוצרים עוברים המרה ל-embeddings
   ונשמרים במאגר וקטורי בזיכרון (WF6, WF7)
2. **שליפה** — שאלת הלקוח הופכת לוקטור, והמערכת מוצאת את הקטעים הקרובים
   ביותר במשמעות
3. **תשובה** — הקטעים נדחפים לתוך ההנחיה, והסוכן עונה מבוסס עליהם בלבד

| מאגר | מקור | קטעים | Chunk / Overlap |
|---|---|---|---|
| `Policies` | 12 מסמכי מדיניות מאוחדים | 157 | 800 / 100 |
| `Products` | `products.csv` | 34 | 800 / 100 |

ב-`Products` נעשה שימוש ב-CSV Loader, ולכן כל מוצר נשמר כקטע שלם —
שליפה מחזירה מוצר עם המחיר והמפרט המלא שלו.

## שכבת הממשק

שני ממשקים, ושניהם מדברים עם **אותה כתובת אחת** — ה-Webhook של WF13:

- **לוח הבקרה** (`dashboard.html`) — דף סטטי יחיד המתארח ב-GitHub Pages.
  מיועד לבעלים, לקריאה בלבד, ונפתח בלחיצה אחת מטלגרם או מהדפדפן
- **אפליקציית הניהול** — נבנתה ב-Lovable. קוראת וכותבת: לידים, חשבוניות,
  מוצרים, משימות וצ'אט עם הסוכן

אף אחד מהם **אינו מחזיק מסד נתונים ואינו מחזיק מפתחות.** הם שולחים JSON
לכתובת אחת ומקבלים JSON בחזרה, כך שה-PAT של Airtable לעולם אינו מגיע
לדפדפן וכל הכללים נאכפים במקום אחד. חוזה הקריאות מתועד ב-[`api-contract.md`](api-contract.md).

## החלטות תכנון

**`InvoiceNumber` כטקסט ולא כמספר.** שדה מספרי אינו יכול להחזיק אפסים
מובילים או קידומת, ו-`INV-0001` היה נשמר כ-`1`. זהו גם השדה הראשי של
הטבלה, ולכן שם הרשומה בכל מקום — כולל שם הקובץ בדרייב.

**`Status` כטקסט חופשי ב-Invoices וב-Leads.** עדכון לערך שלא הוגדר מראש
ברשימה נכשל, וזה בדיוק מה שהתהליכים עושים. ב-`Tasks` דווקא נבחר
Single select — שם יש רק שני מצבים סגורים, `Open` ו-`Done`, והרשימה
מונעת שגיאות הקלדה.

**חישוב לפני ניסוח בסוכן המנהל.** מספרים פיננסיים אינם עוברים דרך מודל
שפה — הם מחושבים בצמתים ומגיעים לסוכן מוכנים.

**עדכון רשומות ב-WF13 דרך HTTP Request ולא דרך נוד Airtable.** נוד
Airtable דורש סכימת עמודות ידועה מראש, ולכן אינו יכול לעדכן טבלה
שנקבעת בזמן ריצה. נוד HTTP Request פונה ישירות ל-API של Airtable ולכן
נוד אחד משרת את כל הטבלאות. המחיר: יש להרשות את הדומיין
`api.airtable.com` בקרדנציאל.

**החשבונית נגזרת מהקטלוג ולא מהקלדה.** מזינים `CustomerId`, `Sku`
ו-`Qty` בלבד; WF1 מחפש ב-Products לפי המק"ט, מביא `Name` ו-`Price`,
ומחשב `Amount = Price × Qty` ואחריו מע"מ וסה"כ. כך אי אפשר להוציא
חשבונית על מוצר שאינו בקטלוג, ואי אפשר לטעות במחיר. זה גם הקשר היחיד
במערכת שבו שתי טבלאות באמת מדברות ביניהן.

**המרת החשבונית למסמך Google.** דרייב אינו מציג HTML — הוא מוריד אותו.
לכן WF8 מעתיק את הקובץ שהועלה למסמך Google ושומר קישור `preview`,
וכך לחיצה אחת פותחת חשבונית מס מעוצבת בדפדפן.
